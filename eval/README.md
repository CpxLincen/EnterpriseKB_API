# 评测集：构建与使用指南

评测集用于对「企业知识库助手」的 RAG 问答做**离线回归验证**：每次改动模型、
提示词、切块策略、检索阈值后，跑一遍评测集即可量化判断「回答是否变好 / 变坏」，
避免凭感觉调参。

## 1. 评测集度量什么

| 指标 | 含义 | 对应字段 |
|---|---|---|
| 检索命中率（Citation Recall） | 回答引用的 Top5 文档里是否包含预期来源 | `expected_sources` |
| 块级检索（Chunk Recall@5 / Hit@k / MRR） | 答案所在**正确块**是否进入 Top5 及其位次 | `expected_chunk` |
| 事实覆盖率（Fact Accuracy） | 回答是否包含预期关键事实（子串匹配） | `expected_facts` |
| 拒答正确率（No-Answer Accuracy） | 知识库无依据的问题是否被正确拒答 | `expect_no_answer: true` |
| LLM 裁判准确率（Judge Accuracy，可选） | 用聊天模型对「回答 vs 参考答案」做 0/1 语义判分 | `reference_answer` + `--judge` |

前两项是「确定性、零额外成本」的硬指标，用于日常快速回归；LLM 裁判用于覆盖
「措辞不同但语义正确」的情况，代价是额外消耗 API。

## 2. 如何构建评测集

评测集是一个 YAML 文件，示例见同目录 `hr-eval.yaml`。构建流程建议如下：

### 2.1 从真实文档与真实用户问题出发

1. 收集 30–50 个真实问题（来自同事日常提问、搜索日志、工单等），而不是凭空编造；
2. 问题覆盖文档的各主要章节，避免集中在某一节；
3. 对每个问题，人工在文档中找到「标准答案」与「来源文件」，作为标注。

### 2.2 题目分类

- **factual（事实型）**：文档里能直接找到答案的问题，填写
  `expected_sources`、`expected_facts`、`reference_answer`；
- **negative（无依据型）**：文档里**没有**答案的问题，设 `expect_no_answer: true`
  （不填 facts），用来测「防幻觉 / 正确拒答」；
- 可按需要扩展更多类别（如 `multi_hop` 多跳推理、`comparison` 对比类），
  `category` 字段目前仅用于分组展示，不改变判分逻辑。

每个 factual 题还可填写两个可选项：

- **`expected_chunk`**：答案所在**正确文本块**的特征子串（短句，如 `满20年的，享受15天`）。
  填写后评测会计算「正确块是否进入 Top5 及其位次」，得到 **Recall@5 / Hit@1 / Hit@3 / MRR**，
  比仅看文件名的「检索命中率」更能反映检索精确度。子串匹配已忽略空白与大小写，
  因此跨行（如 PDF 换行）也能命中。
- **`difficulty`**：难度标签 `L1 / L2 / L3`，仅用于统计分组（报告会按难度分层展示 Recall@5）。

如一道题需要指定与顶层不同的知识库，可加 `knowledge_base: <库名>`（默认取评测集顶层的
`knowledge_base`），这样一份评测集可以同时覆盖多个知识库。

### 2.3 关键事实怎么写

`expected_facts` 是**必须出现在回答里的关键信息**，写短词、短句，不要写整段：

- 好：`"5天"`、`"一个工作日"`、`"电话"`、`"补交"`；
- 差：`"员工累计工作满1年不满10年的，享受5天带薪年休假"`（太长，措辞一变就误判）。

匹配时已做归一化：忽略所有空白与大小写，因此 `"5 天"` 与 `"5天"` 会被视为一致。
同一条事实若有多种等价写法，建议只写最关键、最稳定的核心词。

### 2.4 难度梯度（可选，但推荐）

每道题可加一个 `difficulty` 难度标记：

- **L1 原文原句**：问题与文档句子高度重合（如 `hr-001`）；
- **L2 改写提问**：同义改写、换个说法问（如把「提前多久」改成「需要预留多长时间」）；
- **L3 推理/边界**：需要跨句判断，或落在档位边界（如「满 10 年」恰好切换档位）。

分层后可以分别统计各难度的通过率，看清系统到底卡在哪一类问题。

## 3. 如何使用

### 3.1 前置条件

- 数据库已启动且目标知识库已导入（`python -m app.cli ingest ... --knowledge-base hr`）；
- `.env` 已配置 `QWEN_API_KEY`（Embedding 与回答模型需要）。

### 3.2 运行（零成本，默认）

```powershell
# 方式一：独立入口（默认评测集 eval/hr-eval.yaml）
.\.venv\Scripts\python.exe -m app.eval

# 方式二：走 CLI
.\.venv\Scripts\python.exe -m app.cli eval

# 指定评测集
.\.venv\Scripts\python.exe -m app.eval eval/hr-eval.yaml
```

输出示例（控制台）：

```text
========================================================================
评测结果汇总：共 6 题，作答 4 题，拒答 2 题
  检索命中率（Citation Recall）: 4/4 = 1.0
  事实覆盖率（Fact Accuracy）  : 4/4 = 1.0
  拒答正确率（No-Answer Acc）  : 2/2 = 1.0
========================================================================
[PASS] hr-001 (factual) 员工累计工作满 8 年，每年能享受几天带薪年假？
  回答: 5 天带薪年休假。[1]
  引用: employee-handbook.md
  检索: 命中（预期 ['employee-handbook.md']）
  事实: 通过  命中 ['5天']
...
```

### 3.3 启用 LLM 裁判（额外消耗 API）

```powershell
.\.venv\Scripts\python.exe -m app.eval --judge
```

LLM 裁判用聊天模型对每道有 `reference_answer` 且已作答的题打 0/1 分，用于
「语义等价但措辞不同」的场景。注意：裁判本身也是模型，结果存在噪声，
建议只作为事实指标的补充，而非唯一依据。

### 3.4 输出报告文件

```powershell
.\.venv\Scripts\python.exe -m app.eval --json out/eval-result.json --markdown out/eval-report.md
```

- `--json`：逐题结果 + 汇总，便于入库、画趋势图、接入 CI 做历史对比；
- `--markdown`：人类可读的报告，便于发给团队或存档。

## 4. 何时跑评测

- 修改 `SYSTEM_PROMPT`、切块参数（`size/overlap`）、检索 TopK、`retrieval_threshold` 之后；
- 切换回答模型（`active_provider`）或升级 Embedding 模型之后；
- 新增 / 删除 / 重建知识库索引之后；
- 每次发布前作为回归门禁（可接入 CI，失败即阻断）。

## 5. 注意事项

1. 事实匹配是「子串包含」：若事实词太短（如单个数字 `"5"`）会大量误判，请写足够区分度的词；
2. `expected_sources` 里写的是**入库时记录的文件名**（`employee-handbook.md`），
   与导入文件原名保持一致，否则检索命中会误判为未命中；
3. 更换 Embedding 模型/维度后，旧知识库需重建索引，否则评测会因向量维度错配而报错；
4. 评测结果反映的是「当前知识库 + 当前模型 + 当前阈值」的整体表现，定位问题时
   建议结合单题输出逐条排查（先看检索是否命中，再看事实是否覆盖，最后看裁判）。

## 一、记忆分层总览

判断标准：本项目核心场景是「员工查制度」，因此优先级：**会话内短期 > 跨会话长期 > 知识沉淀**。

| 层次 | 记住多久 | 记住什么 | 现状 |
|---|---|---|---|
| 会话持久化 | 永久（落库） | 每轮问/答、引用、门禁判定 | ✅ 已完成（09-11，`conversations` / `conversation_messages`） |
| 会话内短期记忆 | 单次会话内 | 前几轮上下文，支撑追问、指代消解 | ✅ 已完成（本次，方案 D） |
| 跨会话长期记忆 | 永久、跨会话 | 用户身份 / 偏好 / 习惯，支撑个性化 | ❌ 未做（建议先做「结构化画像」轻量版） |
| 知识沉淀 | 永久、进知识库 | 对话中值得沉淀的可复用事实 | ❌ 未做（属增强项） |

## 二、场景一：会话内多轮追问（短期记忆）

**典型场景**：用户问「合同金额 100 万以上谁审批？」，接着问「那 100 万以下的呢？」——
第二个问题脱离了检索语境，需要把历史带进去才能答对。

| 方案 | 做法 | 优点 | 代价 / 风险 | 适用 |
|---|---|---|---|---|
| A. 最近 N 轮原文回填 | 把最近 N 轮 user/assistant 文本直接拼进 prompt | 实现最简单，指代消解强 | token 随轮数线性涨；历史旧引用易与新检索混淆；不改写则「100万以下的呢」检索不到 | 轮数少、要快 |
| B. 查询改写（Query Rewriting） | 追问先让 LLM 结合历史改写为独立问题，再走现有检索 | 检索质量最高，引用干净、来源可溯源 | 每轮多一次 LLM 调用（成本 + 延迟）；依赖改写质量 | RAG 场景首选 |
| C. 滚动摘要（Summary Memory） | 历史逐轮压缩成摘要，只带摘要 + 最近 1-2 轮原文 | token 可控，长对话不爆窗口 | 摘要丢细节、可能丢关键数字（金额 / 文号）；引用易失真 | 超长对话 |
| D. 混合：改写 + 短窗口原文 + 引用复用 | B 为主，加最近 1-2 轮原文做指代补充；纯加工类追问复用上一轮引用 | 检索准 + 指代稳 + 引用可追溯 | 复杂度最高，要定义「何时复用引用」 | 生产级首选 |

**关键设计点**：
1. **是否重新检索**：追问若沿用上一轮检索结果，引用归属要标「复用上一轮」；否则走改写后检索。
2. **引用归属**：多轮回答的 `[1][2]` 要能追溯到具体哪一轮的 `citations`（JSONB 已存好，可复用）。
3. **历史写入位置**：改写 / 摘要所需历史，从 `conversation_messages` 取最近 N 条即可，**无需新表**。

**选定方案：D（混合）**，详细设计见第四节。

## 三、场景二：跨会话长期记忆（用户画像 / 偏好）

**典型场景**：记住「我是财务部的」「我常查合同金额审批」「我偏好看条文原文而不是大白话」，
下次跨会话直接适用。

| 方案 | 做法 | 优点 | 代价 / 风险 | 适用 |
|---|---|---|---|---|
| A. 结构化画像表 | 新建 `user_profiles` 表存固定槽位（部门、角色、偏好回答风格、常用知识库） | 确定性高、可控、审计友好、零额外检索 | 槽位要预定义，扩展需改表 | 企业内网、字段已知（推荐先做） |
| B. 记忆库（向量检索式） | 「重要记忆」写成自然语言条目 + 向量，回答时检索相关记忆注入 prompt | 灵活、可自然语言扩展 | 多一路检索 + embedding 成本；可能检索到无关 / 过时记忆；需「记忆淘汰」机制 | 长期灵活积累 |
| C. 摘要式长期记忆 | 每次会话结束后 LLM 生成用户摘要，随会话滚动合并 | 实现中等 | 细节丢失、合并策略复杂 | 需积累到一定量级 |
| D. 混合：结构化为主 + 记忆库补充 | A 存确定字段，B 存少量自由记忆 | 兼顾确定性与灵活 | 两套都要维护 | 成熟期 |

## 四、场景三：对话中沉淀知识（记忆 → 知识库）

**典型场景**：用户在对话中发现「制度里没写，但口头惯例是 X」，希望沉淀为可检索知识。

| 方案 | 做法 | 风险 / 代价 | 适用 |
|---|---|---|---|
| A. 人工标记 → 审核 → 入库 | 用户在界面对某轮回答点「沉淀」，管理员审核后写回知识库 | 最稳、可审计 | 现阶段若做，只建议此方案 |
| B. LLM 自动抽取候选 → 人工审核 | 每轮让 LLM 判断是否含「值得沉淀的事实」，生成候选进审核队列 | 有噪声、需审核界面 | 量级上来后 |
| C. 自动直接入库 | 不加人工直接写知识库 | ❌ 高风险，污染知识库、破坏门禁标定 | 不推荐 |

## 六、方案 D 详细设计（已实现）

### 6.1 数据流

```text
会话内新消息
  → 取最近 N 条历史（conversation_messages，改前）
  → LLM 一次调用：输出 {type, query}
     type ∈ new / followup / reuse
  → 分支：
     new       → 用原问题检索（引用全新）
     followup  → 用 query（改写后的完整问题）重新检索（引用全新）
     reuse     → 不检索，复用上一轮已存 context_chunks 与 citations，直接基于原文作答
  → 生成回答 → 落库（assistant 消息携带 citations + decision + context_chunks）
```

### 6.2 三类意图（由改写 LLM 输出）

| type | 含义 | query | 引用 |
|---|---|---|---|
| `new` | 与历史无关的全新问题 / 首问 | 原问题 | 本轮新检索 |
| `followup` | 承接前文、省略 / 指代前文实体，需要新证据 | 改写后的完整独立问题 | 本轮新检索 |
| `reuse` | 不引入新证据需求，仅对上一轮回答加工 | 空 | 复用上一轮 citations |

### 6.3 何时复用引用——判定规则（可落地、可审计）

**核心判据不是「像不像上一轮」，而是「是否引入了新的证据需求」**：

- 只要需要新事实 / 新对象 / 新金额 / 新条件 / 新时间 → **followup**（重新检索，引用全新）；
- 只要是对既有回答本身的加工（展开、举例、总结、翻译、换个说法、解释某一条）→ **reuse**（引用 = 上一轮，且基于已存 chunk 原文作答，保证能「展开」）。

**确定性兜底（不依赖 LLM 判断也成立）**：

1. 会话首条消息（无历史）→ `new`，无历史可复用；
2. `reuse` 必须满足：上一轮 assistant 消息存在、且 `context_chunks` 与 `citations` 均非空；
   否则**降级为 `followup`**（改写重检，改写失败则用原问题检索）；
3. 改写 LLM 输出解析失败 / 字段缺失 / 类型非法 → 降级为 `new`（原问题直接检索），保证永不因改写而中断问答。

### 6.4 LLM 输出协议（结构化 JSON）

```json
{"type": "new|followup|reuse", "query": "改写后的完整检索问题（reuse 时为空字符串）"}
```

解析时从原始文本中截取第一个 `{` 到最后一个 `}` 再 `json.loads`，失败按 6.3 兜底。

### 6.5 数据模型变更

- `conversation_messages` 新增 `context_chunks`（JSONB，可空）：存本轮检索到的完整文本块
  （`knowledge_base / filename / page_number / chunk_index / content / excerpt`）。
  **目的**：`reuse`（如「展开讲讲」）需要上一轮检索的**完整原文**，而 `citations` 只存了 280 字摘要，
  不足以支撑展开。该字段不向前端暴露（`_serialize_message` 不序列化它）。
- 通过 `init_db()` 幂等 `ALTER TABLE conversation_messages ADD COLUMN IF NOT EXISTS context_chunks JSONB` 补齐旧库。

### 6.6 配置（`config/models.yaml` 的 `memory` 段）

```yaml
memory:
  enabled: true              # 关闭则退回单轮问答
  max_history_messages: 6    # 改写时回看的历史消息条数（user/assistant 交替）
  evidence_window_rounds: 3  # reuse 时合并最近几轮 assistant 的检索块（证据窗口，按块去重）
```

### 6.7 涉及文件

- 新增 `app/services/memory.py`：`build_turn_plan()`（历史加载 + 改写判定 + 兜底）、改写提示词、
  `merge_chunk_lists()` / `_recent_evidence_windows()`（方案 A 证据窗口）;
- 修改 `app/services/rag.py`：`serialize_chunks()` / `context_from_stored_chunks()` /
  `citations_from_stored_chunks()` / `answer_from_stored()` / `iter_answer_reuse_events()`；
  `iter_answer_events()` 增加内部 `chunks` 事件（供落库，前端不感知）；
- 修改 `app/routers/conversations.py`：会话内问答（非流式 / 流式）接入 `build_turn_plan`，
  落库 `context_chunks`；
- 修改 `app/models/conversation.py`、`app/core/database.py`、`app/core/config.py`、`config/models.yaml`。

### 6.8 成本与延迟说明

- 每条会话内消息（非首条）会额外调用一次聊天模型做改写（同步，流式开始前完成）；
- `max_history_messages` 控制回看窗口，避免历史过长撑爆 prompt；
- `evidence_window_rounds` 控制 reuse 时合并的最近轮数，越大证据越全、上下文越长；
- `memory.enabled=false` 可整体关闭，完全回到单轮行为。

## 八、会话内记忆的局限与升级方案（2026-09-13 梳理，供用量上来后选型）

### 8.1 当前实现的实际行为

| 维度 | 行为 |
|---|---|
| 理解上下文（指代消解） | 改写 LLM 回看 `max_history_messages`=6 条消息（约最近 3 轮） |
| 证据复用 | 方案 A 后：合并最近 `evidence_window_rounds`=3 轮 assistant 的检索块并去重 |
| 回答带入的历史 | reuse 回答 prompt 带最近 6 条历史文本（仅用于理解所指，回答以资料为准） |

### 8.2 当前方案的局限

1. 固定窗口截断：超过窗口的更早轮次指代会丢失；
2. 指代消解靠一次 LLM 输出：多跳追问（“上一轮提到的那个部门，他们的报销标准？”）可能改写不完整；
3. 跨轮引用编号各自从 `[1]` 起，合并展示时可能混淆（当前前端按轮展示，暂未暴露）；
4. 证据窗口是「按轮数」而非「按语义相关性」合并，无关轮次可能被一并带进上下文。

### 8.3 升级方案清单

| 方案 | 做法 | 收益 | 成本 | 状态 |
|---|---|---|---|---|
| A. 证据窗口 | 最近 N 轮检索块去重合并，随问题一起作资料 | 支持「对比 / 综合多轮」追问 | 低 | ✅ 已实现 |
| B. 结构化指代消解 | 改写输出 `{type, query, hops, ref_rounds}`，按 `ref_rounds` 决定并入哪些轮次 | 多跳追问更准、窗口更聚焦 | 中 | 待选型 |
| C. 滚动摘要 + 关键事实条 | 超窗旧轮压缩成摘要，关键数字/条款号抽成结构化事实条保留 | 长对话不丢关键信息、token 可控 | 较高 | 待选型 |
| D. 结构化对话状态（槽位） | 维护当前话题槽位（合同类型/金额档位/审批人…），追问先填槽再检索 | 适合结构化重复问答 | 中 | 待选型 |
| E. 跨会话长期记忆 | 结构化画像 / 向量记忆库 / 知识沉淀 | 跨会话个性化 | 中-高 | 待选型 |
| F. 通用工程做法 | 记忆即检索、自动压缩（reflexion）、Graph 记忆 | 通用但偏重 | 高 | 参考 |

### 8.4 推荐

用量上来后优先 **B 轻量版**（让证据窗口按 `ref_rounds` 聚焦，而非无差别合并最近 N 轮）；
C/D 视「长对话」与「结构化重复问答」的实际占比再评估；E/F 等有跨会话个性化诉求时再做。

## 九、方案 A：证据窗口（已实现）

- **配置**：`config/models.yaml` 的 `memory.evidence_window_rounds`（默认 3）。
- **实现**：`app/services/memory.py` 的 `merge_chunk_lists()` 与 `_recent_evidence_windows()`；
  reuse 分支由「复用最近一条 assistant 的 `context_chunks`」改为「合并最近 N 轮并去重」。
- **去重键**：`(knowledge_base, filename, chunk_index)`；**顺序**：最新一轮在前。
- **效果**：reuse 类追问（如「对比刚才两条」「综合上面几轮」）可拿到多轮证据原文，
  引用由 `citations_from_stored_chunks()` 从合并后的块重建，编号与上下文 `[i]` 对齐。

# 会话持久化与规模化演进方案

> 记录时间：2026-09-11
> 状态：本文档为**规划**，除「已落地」一节外均未实现，供 Agent 规模变大时按阈值逐级演进。

## 一、已落地（本次迭代）

会话持久化当前实现：

- 两张表：`conversations`（会话元数据 + `status/archived_at` 生命周期字段）、
  `conversation_messages`（完整消息文本 + 引用 JSONB + 门禁判定）；
- **消息游标分页**：`GET /conversations/{id}?limit=&before_id=`，返回 `total / has_more / messages`，
  前端「加载更早」按 `before_id` 键值游标向前翻页（对实时追加的新消息免疫，避免 OFFSET 漂移）；
- **归档**：软归档 `status=archived`（可恢复），`POST .../archive` / `.../unarchive`，
  列表可按 `active / archived / all` 过滤；
- **保留策略**：`CONVERSATION_ARCHIVE_DAYS`（活跃会话超期自动归档）、
  `CONVERSATION_RETENTION_DAYS`（归档会话超期永久删除，连同消息），
  触发入口为启动钩子 / `POST /conversations/retention/run` / `python -m app.cli retention`。

上述即为「分页 + 归档/保留」的第一阶段，足以支撑当前体量。下面按规模阈值给出后续演进方向。

## 二、规模增长的瓶颈预估

按「每轮问答 = 用户消息 + 助手消息」两行、每行约 0.5~5 KB 估算，单租户累积：

| 消息总量 | 估算体积 | 主要瓶颈 |
|---|---|---|
| < 10 万条 | < 0.5 GB | 无，现状即可 |
| 10 万 ~ 100 万 | 0.5~5 GB | 单表扫描变慢、冷数据占库、引用摘要重复膨胀 |
| 100 万 ~ 1000 万 | 5~50 GB | 全表检索/聚合变慢，需要冷热分层与分区 |
| > 1000 万 / 多租户 | > 50 GB | 需要分库分表、独立检索、异步落库 |

关键点：**消息文本本身很小，真正的压力不在磁盘容量，而在「查询性能、重复数据、冷数据长期占用热库、以及全量检索能力」**。

## 三、分级演进方案

### L1（10 万~100 万）：索引优化 + 引用去重 + 时间分区

1. **时间分区表**：`conversation_messages` 按 `created_at` 做 PostgreSQL RANGE 分区（按月/季度），
   老分区可整体 DETACH 归档或 DROP，删除不再逐行扫；`conversations` 亦可用小粒度分区。
2. **引用去重**：把每条回答里的 `citations` 从「完整 JSONB 摘要」改为
   `chunk_id 外键 + 页码/块序号`，摘要**按需实时生成**（或缓存一份在 chunk 侧），
   避免同一文档块被多轮引用时摘要被重复存储（当前是唯一会线性膨胀的重复数据）。
3. **索引**：`conversation_messages(conversation_id, id)` 复合索引（当前已有单列）、
   `conversations(updated_at)`/`created_at` 可改 BRIN（时间单调，体积小、扫描快）。
4. **审计表同样治理**：`audit_logs` 也是只增表，纳入同一套保留策略与分区。

### L2（100 万~1000 万）：冷热分层 + 外置存储 + 全文检索

1. **消息体外置**：`content` 大文本从行内移到**对象存储**（MinIO / S3），
   数据库只存 `message_key + 元数据 + 引用`；热数据保留在 DB，冷数据按需回读并做本地缓存。
2. **冷归档落盘压缩**：过期会话导出为 **Parquet + 压缩**（或 gzip JSONL）存对象存储，
   DB 只留「会话索引 + 位置指针」，需要时按会话回放，长期保存成本降到 1/10 以下。
3. **历史会话检索**：为消息加全文索引（Postgres `tsvector` + jieba 分词，或 `pg_trgm` 做模糊；
   规模再上走 **OpenSearch/Elasticsearch**），支持「搜到过哪句话 / 什么时候问过」。
4. **读写分离 / 缓存**：读多写少，列表与详情读走只读副本；热点会话列表结果进 Redis。

### L3（> 1000 万 / 多租户）：分库分表 + 事件化

1. **多租户隔离**：按 `user_id`（或租户）水平分片（sharding），单租户数据物理隔离、可独立备份/清理。
2. **异步落库**：问答完成后消息写入走**消息队列**（Kafka / NATS），由消费者批量落库，
   削峰并解耦「回答返回」与「持久化」的延迟；失败可重试，保证不丢消息。
3. **CDC 事件流**：消息落库后产出变更事件，供审计、数据分析、记忆模块等下游订阅。
4. **独立检索/归档服务**：检索与冷归档从主问答链路剥离为独立服务，避免互相拖累。

## 四、与「Agent 记忆」的关系（下一步的自然延伸）

会话持久化只解决「记录不丢」。当 Agent 需要**多轮追问、长期记忆、跨会话回忆**时：

- **短期记忆**：最近 N 轮作为上下文回传，需要 query 改写 / 指代消解 + 上下文截断；
- **长期记忆**：对历史消息做**摘要 + Embedding**，单独存一张记忆向量表（可复用现有 pgvector 管线），
  追问时先检索相关记忆再拼上下文；
- **记忆也要生命周期**：记忆条目同样需要「重要度评分 + 保留策略 + 过期清理」，
  与本文档的归档/保留策略保持同一套治理框架。

> 注意：记忆向量表会引入**新的向量存储成本**（每条记忆 1024 维），届时它的体积将显著大于消息文本，
> 需要独立评估保留策略（例如只保留摘要、不保留原始消息向量）。

## 五、落地节奏建议

| 阶段 | 触发条件（经验值） | 优先动作 |
|---|---|---|
| 现在 | 单租户 < 10 万条 | 保持现状，观察 `conversation_messages` 增长曲线 |
| 近期 | 消息 > 10 万条，或详情页变慢 | 引用去重 + `(conversation_id, id)` 复合索引 |
| 中期 | 消息 > 100 万条，或冷数据占库过半 | 时间分区 + 冷归档（Parquet/对象存储）+ 消息体外置 |
| 远期 | 多租户 / > 1000 万条 | 分库分表 + 异步落库 + 独立检索服务 |

## 六、技术选型参考

| 能力 | 候选方案 | 备注 |
|---|---|---|
| 分区 | PostgreSQL 原生 RANGE/LIST 分区 | 无需新组件，优先 |
| 对象存储 | MinIO（私有化）/ S3 | 冷归档、消息体外置 |
| 冷数据格式 | Parquet + gzip/zstd | 体积小、可按列分析 |
| 全文检索 | PG `tsvector` + jieba → OpenSearch | 先 PG 后迁，避免过早引入 |
| 异步队列 | NATS / Kafka | 仅 L3 需要 |
| 缓存 | Redis | 热点列表/会话元数据 |
| 调度 | 系统 cron / Airflow | 保留策略、冷归档任务定时跑 |

> 原则：**先索引与去重，再分区与冷分层，最后才考虑分库分表与消息队列**——
> 每上升一级都引入新的运维复杂度，必须有对应规模数据支撑。

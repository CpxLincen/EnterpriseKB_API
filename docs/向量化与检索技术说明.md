# 企业知识库助手 · 向量化与检索技术说明

> 本文档描述项目「企业知识库助手」（后端 `E:\EnterpriseKB`）在**文档向量化（入库）**与
> **检索（问答）**两个环节采用的处理方式，参数以 `config/models.yaml` 当前配置为准。

---

## 总览

```text
┌──────────────────────────── 入库（Ingestion）────────────────────────────┐
文档(.md/.txt/.pdf) → 读取文本 → SHA-256 去重 → 语义切块 → 批量 Embedding → pgvector 入库

┌──────────────────────────── 检索（Retrieval）────────────────────────────┐
用户问题 → 问题向量化 → 稠密检索(pgvector 余弦) + 稀疏检索(BM25)
        → RRF 融合 →（可选）BGE Rerank → top_k → 组装上下文 → LLM 回答 + 引用
```

核心思路：**稠密向量负责语义相关，BM25 稀疏负责精确词面命中（专有名词、编号等），
RRF 融合两路候选，BGE 交叉编码器再做精排**，最终把最相关的少量文本块交给大模型作答。

---

## 一、文档向量化（入库）的处理方式

入口：`app/ingestion.py` 的 `ingest_file()`。

```text
读文件 → 内容哈希去重 → 校验模型 → 切块 → 批量 Embedding → 写入 pgvector
```

### 1. 读取文档（`read_document()`）

| 类型 | 处理方式 |
|---|---|
| PDF | 用 `pypdf` **逐页**提取文本，页码从 1 开始记录；页面无文字时提取为空字符串 |
| Markdown / TXT | 整篇读取，优先 **UTF-8**；失败降级 **GB18030**（兼容中文 Windows 的 GBK/GB2312）；两种编码都失败则明确报错 |

### 2. 内容哈希去重

- 对文件**原始字节**计算 SHA-256，存入 `documents.content_hash`；
- 同一知识库内哈希相同 → 视为已导入，直接跳过（返回 0），避免重复入库。

### 3. Embedding 模型一致性校验

- 新建知识库时记录 `embedding_model` 与 `embedding_dimensions`；
- 每次导入/问答都会校验当前配置与知识库一致，防止 pgvector 向量维度错配。

### 4. 语义切块（`chunk_text()`）

| 参数/规则 | 取值 |
|---|---|
| 目标块大小 | 650 字符 |
| 相邻块重叠 | 80 字符 |
| 断点优先级 | 换行 > 句末标点（。！？）> 停顿（，；、）> 空格 |
| 硬切条件 | 找不到合适断点（断点位置不足半块）时才硬切 650 |
| 碎片过滤 | 丢弃长度 ≤ 20 字符的残留 |
| 预处理 | 3 个及以上连续换行压缩为 2 个；去首尾空白 |

- 优先在**自然断点**断开，避免切断句子；
- 下一块从上一块结尾**往前回退 80 字**开始，保证跨块语义衔接。

### 5. 批量生成 Embedding（`app/providers.py`）

- 调用 **Qwen `text-embedding-v4`**（OpenAI 兼容接口，1024 维）；
- 所有文本块**一次性批量请求**，响应顺序与输入一致；
- 聊天模型与 Embedding 模型分离配置（DeepSeek 无 Embedding 时自动回落 Qwen）。

### 6. 写入数据库（`app/models.py`）

每个文本块生成一条 `document_chunks` 记录：

| 字段 | 含义 |
|---|---|
| `content` | 文本块内容 |
| `page_number` | 页码（非 PDF 为 NULL） |
| `chunk_index` | 块在文档内的序号（从 0 开始） |
| `embedding` | pgvector 的 `Vector` 类型（1024 维） |

最后一次性 `commit`，并使该知识库的 BM25 缓存失效（`retrieval.invalidate`）。

## 二、检索（问答）时的处理方式

入口：`app/rag.py` 的 `ask()` + `app/retrieval.py` 的 `hybrid_search()`。

```text
问题向量化 → 稠密检索(pgvector 余弦) + 稀疏检索(BM25)
           → RRF 融合 →（可选）BGE Rerank → top_k → 上下文组装 → LLM 回答 + 引用
```

### 1. 问题向量化

用户问题用**同一个 Embedding 模型**（Qwen `text-embedding-v4`，1024 维）转成向量，
保证与文档块处于同一向量空间。

### 2. 稠密检索（语义匹配）

- 在 pgvector 中用 `cosine_distance` **升序**取前 `candidates=20` 个候选；
- 距离 = 1 − 余弦相似度，越小越相关。

### 3. 稀疏检索（关键词匹配，`Bm25` 类）

- 标准 **Okapi BM25**（k1=1.5，b=0.75）；
- 分词 `tokenize()`：
  - **中文按字符二元组**：`年假如何计算` → `年假 / 假如 / 如何 / 何计 / 计算`；
  - 英文/数字按整词，统一小写；
- 同样取前 `candidates=20` 个候选；
- BM25 索引**按知识库缓存在进程内存**，文档入库/删除时自动失效重建。

> 两路互补：稠密路捕捉语义相关，稀疏路捕捉精确词面（专有名词、编号、工号等）。

### 4. RRF 融合（Reciprocal Rank Fusion）

- 两路候选各自按排名贡献 `1 / (k + rank)`（`k = rrf_k = 60`），同一块分数叠加；
- 取两路候选的**并集**，按融合分数重新排序（分数相同时按稠密距离升序兜底）。

### 5. 三种检索方式（`mode` 可切换）

| mode | 行为 |
|---|---|
| `dense` | 纯向量：直接取稠密前 top_k |
| `hybrid` | RRF 融合后取前 top_k |
| `rerank` | RRF 前 `rerank_candidates=10` 个候选送 BGE 交叉编码器精排，再取前 top_k |

- 最终返回给大模型 **`top_k=5`** 个文本块；
- 缺省检索方式：开启 rerank 时为 `rerank`，否则为 `hybrid`；
- 前端评测页可一键跑三种方式对比指标。

### 6. BGE Rerank（`app/rerank.py`）

- 模型：**`bge-reranker-v2-m3`**（多语言、中文强，交叉编码器逐对打分）；
- 本地路径：`E:\EnterpriseKB\models\bge-reranker-v2-m3`；
- 精度：`fp16: auto`（有 CUDA 自动开半精度）；当前 torch 为 `2.13.0+cu126`，
  Rerank 已运行在 **GPU（cuda:0 + float16）**，单次推理约 29ms；
- 按模型名进程内懒加载缓存。

### 7. 防幻觉门禁（`app/rag.py` 的 `should_refuse`）

以**稠密距离为主、Rerank 分为辅**，规则按优先级：

1. 无候选 → 拒答；
2. 稠密最近距离 ≤ `retrieval_threshold`（0.65）：
   - 开启 rerank 且最高重排分 < `gate.rerank_floor`（0.05）→ 判为“语义太弱”，拒答（收紧）；
   - 否则放行；
3. 稠密最近距离 > 阈值（本应拒答）：
   - 开启 rerank 且最高重排分 ≥ `gate.rerank_rescue`（0.5）→ “重排救援”放行（防止 BM25/Rerank 强命中被误拒）；
   - 否则拒答。

阈值 `rerank_floor` / `rerank_rescue` 按当前 Embedding 模型与知识库标定（见
`eval/gate-signals.tsv` 的信号分布），更换 Embedding 模型后需重新标定。

### 8. 上下文组装与 Prompt 注入防护（`SYSTEM_PROMPT`）

- 每个块编号，附「文件名、页码、内容」，整体用 `<资料>…</资料>` 标签包裹；
- 系统提示词明确：只依据资料回答、资料是不可信数据（拒绝“忽略指令/泄露资料/扮演角色”等注入）、
  资料不足时拒答、每个结论保留引用标记（如 [1]）。

### 9. 生成回答

- 调用聊天模型 **Qwen `qwen-plus`**（`temperature=0.1` 低温稳定输出）；
- 返回 `(回答, 引用列表)`；引用项含文件名、页码、块序号、前 240 字摘要。

## 五、当前限制与后续扩展（2026-09-10 待办）

> 本节为 2026-09-10 补充，记录入库/检索环节的已知限制与规划，**仅规划、暂不实现**；
> 详细方案见 `docs/待解决问题与解决方案.md`。上文正文为早期快照，
> 09-08 分层重构后个别文件已迁移（如 `app/ingestion.py` → `app/services/ingestion.py`），
> 以当前代码为准。

### 5.1 入库侧：文档类型与多模态内容（对应「问题三」）

- **已支持**：`.md / .txt / .docx / 文字型 PDF`；
- **待扩展格式**：`.xlsx`（openpyxl）、`.pptx`（python-pptx）、`.html/.epub`；
  PDF 建议引入 pymupdf 更好还原版面与表格；
- **表格**：统一转 Markdown 表格文本，保留行列结构；
- **图片/图表**：OCR + 版面分析 + VLM 生成文字描述后走现有向量管线（轻量路线），
  进阶再引入 CLIP 等视觉向量做多路检索；引用保留页码/图号可回看原图；
- **扫描 PDF**：OCR + 版面分析先行，再走现有流程；
- **块类型扩展**：`DocumentChunk` 增加 `content_type`（text / table / image）。

### 5.2 检索侧：跨知识库与自动路由（对应「问题二」）

- 现状：`/chat` 的 `knowledge_base` 必填，由用户选库；
- 规划：`knowledge_base` 改为可选，为空时自动路由——候选为当前用户**有读权限**
  的全部知识库；库少时直接「全库聚合检索」，库多时「先轻量选库 → 再精检」两阶段；
- 引用需携带 `knowledge_base`，跨库结果统一做防幻觉门禁与来源标注。

### 5.3 会话持久化（对应「问题一」，不在本文档范围内）

- 问答记录的持久化属「会话/消息」层，与本检索专题无关，详见
  `docs/技术全景与学习手册.md` 第九节与 `docs/待解决问题与解决方案.md`。

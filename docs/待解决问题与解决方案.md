## 问题一：问答记录未持久化（切换页面后记录消失）

> 状态更新（2026-09-13）：会话持久化（09-11）与**会话内短期记忆 / 多轮追问（方案 D）**均已实现，
> 记忆策略、方案选型与「何时复用引用」判定规则见 [`docs/记忆策略与方案.md`](记忆策略与方案.md)。
> 跨会话长期记忆与知识沉淀尚未实施，见该文档第七节的分阶段路线。

### 现状与根因

- 前端 `ChatPage` 用 React `useState` 保存消息，路由切换导致组件卸载，消息随之丢失；
- 后端无「会话 / 消息」表，也没有会话查询接口；
- 本质是缺少**会话持久化**，而不是单纯的"没存到本地"。

### 关键澄清：用户所说的"记忆模块"其实是两层，应分开规划

| 层 | 含义 | 解决的问题 |
|---|---|---|
| 会话持久化（Conversation Persistence） | 把会话与消息存到数据库，可回看、可续接、可审计 | 记录消失 |
| 对话记忆（Multi-turn Memory） | 把最近 N 轮问答作为上下文回传给模型，支持追问 | 多轮追问、指代消解 |

两者不同，也都有价值；当前痛点只属于第一层。

### 方案（会话持久化）

1. **数据模型**（后端新增两张表）：
   - `conversations`：`id / user_id / title(首问截断) / knowledge_base(可空) / created_at / updated_at`
   - `conversation_messages`：`id / conversation_id / role(user|assistant) / content / citations(JSONB) / decision / created_at`
2. **API**：
   - `GET  /conversations`（当前用户会话列表）
   - `POST /conversations`（新建会话）
   - `GET  /conversations/{id}/messages`（某会话消息）
   - `POST /conversations/{id}/chat`（会话内问答，服务端落库；可复用现有 `/chat` 与 `/chat/stream` 逻辑）
   - `DELETE /conversations/{id}`
3. **前端**：侧边栏新增「历史会话」列表 + 「新建会话」；进入会话时拉取历史消息；路由切换不再丢失。
4. **权限与审计**：会话归属 `user_id`，普通用户只见自己的会话，管理员可查全部；问答落库与审计日志联动。

### 方案（多轮记忆，第二阶段、可选）

- 追问时把最近 N 轮作为上下文回传；需要额外处理：
  1. **是否需要重新检索**：追问往往是对上文的指代（"那 100 万以下的呢？"），需要 query 改写或判断是否沿用上一轮检索结果；
  2. **引用归属**：多轮回答的引用要能追溯到具体哪一轮的检索块；
  3. **上下文窗口控制**：历史轮次截断策略，避免 token 超限。
- 建议：先做「会话持久化」（直接解决痛点、改动可控），「多轮记忆」单独立项。

## 问题二：提问前必须先选知识库，员工不知道选哪个

> 状态更新（2026-09-11）：已实现「全库聚合检索 + 可选手动指定」——
> 后端 `knowledge_base` 改为可选（空 / "auto" 自动路由到当前用户全部可读库），
> 引用与上下文中标注来源知识库；前端知识库选择器默认「自动（推荐）」。

### 现状与根因

- `/chat` 请求体的 `knowledge_base` 必填，前端下拉必选；
- 根因：知识库是**技术实现细节**，不该暴露给普通用户做"路由决策"——员工只关心问什么，不关心答案存在哪个库。

### 方案（推荐：自动路由 + 可选手动指定）

1. **后端**：`/chat` 的 `knowledge_base` 改为可选；为空时自动路由：
   - 候选 = 当前用户**有读权限**的全部知识库；
   - 两阶段路由：
     - 阶段一（轻量选库）：对每个候选库各做一次快速检索（dense top-k 或 BM25 打分），按最高信号取 1~N 个库；
     - 阶段二（精检）：在选中的库里跑完整检索（dense + BM25 + RRF + rerank），跨库融合 top-k；
   - 引用结果中携带 `knowledge_base` 字段，回答可标注"来自《XX制度》"，便于溯源。
2. **更简单的一版（库数量少时首选）**：直接"**全库聚合检索**"——把所有可读库的 chunk 合并后做跨库 top-k，无需选库，也无需路由分类器。
3. **前端**：输入框不再要求选库，默认「自动」；折叠一个「高级」入口供少数需要精确指定库的人使用。
4. **边界**：
   - 自动路由只检索有读权限的库，权限逻辑不变；
   - 「无依据」判定基于聚合后的跨库结果统一做；
   - 多库命中同一主题时，按 rerank 分排序，必要时标注来源库差异。

### 建议

先做「全库聚合检索 + 可选手动指定」（后端把 `knowledge_base` 设为可空，空 = 全部可读库聚合），最贴合"员工只提问"的诉求；等知识库规模变大、聚合检索变慢时，再上「轻量路由/分类器」。

## 问题三：文档类型识别 + 图片/图表/表格内容解析

### 现状与根因

- 已支持：`.md / .txt / .docx / 文字型 PDF`；
- 不支持：`.xlsx / .pptx / .html / .epub / 扫描 PDF`；
- PDF/DOCX 内的**图片、图表、表格**未结构化处理：图片被跳过、表格被按行拍平、图表完全丢失。

### 方案（分层：文本优先 → 表格结构化 → 多模态补充）

#### 第一层：解析格式扩展（文本优先）

| 格式 | 解析方式 | 说明 |
|---|---|---|
| `.xlsx` | openpyxl 逐 sheet / 逐行读取 | 转 Markdown 表格文本 |
| `.pptx` | python-pptx 逐页提取标题/正文/备注 | 保留页序 |
| `.html` / `.epub` | 正文抽取（BeautifulSoup / 专用解析） | 去导航、留正文 |
| PDF | 引入 pymupdf 替代/补充 pypdf | 更好还原版面顺序、识别表格 |

#### 第二层：表格结构化

- DOCX / XLSX / PDF 中的表格统一转成 **Markdown 表格文本**（保留行列结构），
  避免把表内容拆乱或丢失字段对应关系；
- 表格作为一个整体块或"表头+行"切块，嵌入语义信息。

#### 第三层：图片 / 图表（多模态补充，两条技术路线）

1. **路线 A（轻量，推荐先做）：转文本入库**
   - 图片/图表 → OCR（PaddleOCR / 云 OCR）+ 版面分析（PP-Structure / MinerU）+ VLM（如 Qwen-VL）生成**文字描述**；
   - 描述文本切块后走现有向量管线；
   - 引用保留图片位置（页码 / 图号 / 坐标），回答时可跳转原图。
2. **路线 B（进阶，按需再做）：视觉向量多路检索**
   - 用 CLIP 等视觉 Embedding 单独建一路，与文本检索做 RRF 融合；
   - 适合"搜图 / 找图表"类场景。

#### 第四层：扫描 PDF

- OCR + 版面分析先行，把扫描页转成带结构文本，再走现有入库流程；
- 原始扫描图保留，供引用回看。

#### 关键设计点

- **块类型扩展**：`DocumentChunk` 增加 `content_type`（text / table / image），
  image 块存"描述文本 + 原图引用（文件路径/页码/坐标）"；
- **引用可追溯**：图片/图表作为独立块，回答能指回"第 X 页 图 Y"；
- **去重与版本**：图片 hash 去重、文档更新后重建索引、失败重试（与既有待办合并）。

### 建议优先级

1. 先「文本类格式扩展（xlsx/pptx）+ 表格结构化」——收益大、无模型依赖；
2. 再「PDF 图片/扫描 OCR + 图表描述」——依赖 OCR/VLM，需要模型与算力；
3. 视觉向量检索最后按需引入。

| 问题 | 依赖 | 建议节奏 |
